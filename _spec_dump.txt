Problem statement and scope
Procurement needs one decision per vendor — proceed, proceed with safeguards, or decline — made faster and more consistently than manual research allows, and backed by evidence because the output is AI-generated.
The requirement list groups into four layers: the decision itself (risk score + recommended action); the evidence that supports it (global compliance, India regulatory, litigation, ownership and behaviour); a trust constraint that applies across both (every material finding cites its source); and post-decision actions (supplier-engagement pack, ongoing monitoring).
This document covers the full system as it would run in production. The prototype demonstrates the same pipeline end to end on 2–3 sample vendors, using a narrower set of data sources — it proves the pattern works, not that every regulator integration is built.
System architecture

agent pipeline · 6 stages, monitoring loop
The orchestrator routes each vendor by entity type and plans the check sequence; four specialist agents run in parallel; findings pass through an evidence store and guardrail critic that checks every claim against a source before scoring; borderline or decline cases go to a human; and the report triggers an ongoing monitoring loop back to the orchestrator, shown as the dashed line on the left.

Flow, end to end
The vendor intake form captures identifiers, entity type, self-disclosed documents, and the analyst's category weights
The orchestrator routes: decides which checks apply for this entity type, skips the rest
The four specialist agents run in parallel, each calling its own tool; GST is checked manually by the analyst in the same window
Every finding lands in the evidence store, tagged resolved-clean, resolved-red-flag, vendor-declared, unresolved, or confirmed-by-absence
The evidence and guardrail agent confirms every claim has a citation before scoring proceeds
The scoring agent applies the hard-override gate first — an active sanctions match or an SFIO investigation forces a decline outright; everything else goes through weighted scoring
A borderline score, or any decline, goes to a human at the HITL gate
The report and engagement pack are generated, naming unresolved items and what's needed to close them
Monitoring re-triggers the orchestrator on a periodic or event-driven basis

Build-vs-buy for the data layer
Stitching together twelve separate regulator integrations (MCA, GST, eCourts, SEBI, NCLT, EPFO, ESIC, SFIO, RBI/CIBIL, NSE/BSE, MSME, licences) would consume most of a 3-person team's time on data plumbing, leaving little for the actual differentiator — orchestration, evidence-linking, UBO reasoning, and report generation.
Recommendation: OpenSanctions for global sanctions/PEP/adverse media, plus one India KYB aggregator (SignalX or the Karza + Probe42 combination) for the regulatory and litigation rows in the data source table. Build in-house only where an aggregator falls short — for example a dedicated eCourts scraper, if cost at scale makes that worthwhile.
This keeps engineering effort on the agentic layer — the orchestrator's routing logic, the exception-handling framework, evidence-linking, and scoring/report generation — which is what a procurement team cannot buy off the shelf.

Source reliability and confidence
A source returning data is not the same as that data being trustworthy. Every source used feeds into a four-tier confidence model, and the tier — not just the finding — is stored alongside the evidence.

This is why the aggregator selection in Build-vs-buy is not just a cost decision — an aggregator that won't disclose its underlying source caps every finding it produces at tier 3, which changes how much of the report can be auto-approved versus routed to a human.
Freshness: every stored finding carries a fetch/as-of date. Checks are re-pulled on a cadence matched to how fast that source changes — litigation and sanctions/PEP monthly or event-driven, slower-moving registrations (MCA, Udyam) quarterly — rather than being treated as permanently valid after the first pull.
For RBI/CIBIL and SFIO specifically, there is no technical fix — the access restriction is structural, not a data quality problem. The two real options are: (a) a data-sharing or reseller agreement with a licensed credit information company, typically available only to entities with an existing lending relationship, which a pure procurement function usually doesn't have; or (b) accept these as permanently vendor-declared and say so explicitly in every report, rather than letting confidence quietly drift upward over time as the same unverified answer gets repeated across screening cycles.
One more gap this surfaces: scraping government portals (eCourts, MCA, GST) may conflict with the portal's own terms of use. This should get a legal review before production, independent of whether the scraper works technically.

Data storage and tool design
Retry-until-correct only applies to one of the four finding categories. A tool must classify its own failure before deciding whether to retry.
Technical failure (a timeout, a 5xx) — retry, it might succeed next time
Structural gap ("not found" on an unregistered entity) — retrying returns the same answer every time; this is the vendor-ask path, not a retry loop
Ambiguous finding (a low-confidence fuzzy match) — retrying the same query returns the same ambiguous result; this needs a human, not another attempt

Litigation — severity and pattern
Raw case data (court, case number, nature, counterparty, status) isn't itself a risk signal — the read on it is:
Nature: a code like NI Act §138 (cheque bounce) is the most common commercial litigation type in India and, alone, is a mild signal; multiple such cases are not
Court level: District Court / Consumer Forum cases read as lower severity than High Court or NCLT cases
Party role: the vendor as defendant is a more significant signal than the vendor as plaintiff — being sued differs from suing someone
Pattern, recurring counterparty: several cases against the same bank or the same opposing party is a systemic signal, not a coincidence, and should be flagged as a pattern rather than listed as separate unrelated cases
Pending vs disposed ratio: a high share of pending cases can mean slow courts or delaying tactics — worth noting, not automatically penalised, since court delays aren't the vendor's fault
Scoring — weights as an input, not a fixed rule
Rather than hardcoding how much each risk category (compliance, India regulatory, litigation, ownership) counts toward the final score, the analyst sets this per case: after the intake form, a slider lets them weight each category for that specific procurement decision — a one-off purchase order might deprioritise deep UBO scrutiny; a long-term strategic supplier might weight financial health and litigation heavily.
Sensible defaults are shown, not a blank slider — most cases need no adjustment. Every deviation from the default is logged with the case, so that once enough vendors have gone through the system, there's real data to set fixed, principled weights instead of guessing them upfront — the same pattern used for the contract-value threshold.
Two safeguards this needs, or it undermines the consistency and auditability the whole system is built around:
Weights change the aggregate score, never the underlying evidence — a report still shows an SFIO match or a confirmed sanctions hit prominently, regardless of how it's weighted into the top-line number
A small set of findings (an active sanctions match, an SFIO investigation) are hard overrides that force a decline recommendation regardless of weights — nothing should be able to weight these away
